## 0. 最終結論

這次優化不能只做「把幾句話改口語」。完整問題包含四層：

1. **文字排版債：** 前四冊有大量半形標點、管線表格、行首空白與原課本指涉。
2. **資訊結構債：** 後三冊雖然比較口語，但長段落、比喻與對照內容集中在同一欄位，手機上仍像文字牆。
3. **編輯語氣債：** 統計、商管、工程與心理學用語過密；部分對話不像台灣使用者真的會傳。
4. **教學規則債：** 邀約、拒絕、回覆速度、爭執與「測試」在不同冊出現矛盾或過度斷言。

最終建議採用以下方向：

- 先建立新的內容決策與單一真源，再改文案。
- 讓 7 份 assets JSON 成為 App 使用的正式產品文案真源。
- 原夥伴 HTML 轉換器保留，但只產生「匯入候選檔」，不得再直接覆寫正式 JSON。
- 不新增電子書 block type；先用既有 paragraph、heading、bulletList、comparison、entryList、checklist、callout 與 dialogue 完成重排。
- 先修 P0 跨冊規則，再做標點、結構與口吻；否則會把互相矛盾的內容改得更順，卻沒有改對。
- 保留既有書籍、章節、權限、閱讀版型與導覽架構；不碰付費牆邏輯、Edge Function、AI prompt 或發行流程。

建議拆成 8 個可獨立審查與回退的工作包，最後以內容契約、視覺 proof 與 5 人 dogfood 驗收。

## 4. 最終編輯契約

### 4.1 語氣

- 像熟悉台灣交友軟體情境的教練，不像論文、商管簡報或 PUA 黑話詞典。
- 先講讀者現在要看什麼，再講原因。
- 能直接指出問題，但不用「一定、永遠、唯一、完全、最強」製造假確定感。
- 不從一則訊息直接判斷對方人格、情緒或意圖。
- 不把互動寫成高位／低位競賽；需要談方向與界線時，直接說具體行為。
- 不做道德說教；只說這個做法會造成什麼可觀察結果，以及更有效的替代方式。

### 4.2 用詞與角色

| 情境 | 規則 |
|---|---|
| 旁白對男性使用者 | 用「你」 |
| 使用者傳給女性對象的示範訊息 | 用「妳」 |
| 泛指任何聊天對象 | 用「對方」 |
| LINE 品牌 | 全大寫 LINE |
| 訊號 | 一律「訊號」，不用「信號」 |
| 鉤子 | 一律「鉤子」，不用「勾子」 |
| 升溫 | 使用繁體「溫」 |
| English jargon | 中文先出現，必要時再以括號補英文或代碼 |

### 4.3 句子與區塊

| 欄位 | 目標 | CI 上限 |
|---|---:|---:|
| chapter title | 14–18 個中文字內可辨識 | 超過 22 字失敗 |
| entry summary | 10–22 個中文字 | 超過 40 字失敗 |
| dialogue line | 像一則真人訊息 | 超過 80 字失敗 |
| annotation | 一個判讀 | 超過 80 字失敗 |
| caption | 一個結論 | 超過 100 字失敗 |
| bullet item | 一個要點 | 超過 100 字失敗 |
| paragraph | 一個主要意思 | 超過 120 字失敗 |
| callout text | 一個提醒或修正 | 超過 160 字失敗 |

暫時保留的例外必須進具名 allowlist，列出 block ID 與理由；不允許只為了讓 CI 綠而加整本書例外。

### 4.4 統一閱讀節奏

每個主要教學點依序呈現：

1. **結論：** 這一段要注意什麼。
2. **原因：** 最多三點。
3. **例子：** 一個自然對話或對照。
4. **下一步：** 讀者現在可以做什麼。

同一個教學點最多使用一個主要比喻。比喻拿掉後意思就消失，代表原理還沒有說清楚。

## 5. P0 跨冊教學契約

下列文案是整套教材的 canonical rule。任何逐冊改寫都不得與它相反。

### 5.1 判讀優先順序

**定稿：**

> 明確的拒絕或界線，永遠排在最前面。只有字面真的模糊時，才看一段時間內反覆出現的行為，再判斷可能的情緒。不要用猜測推翻對方說出口的答案。

取代：

- 「行為 ＞ 情緒 ＞ 字面」
- 「行為 ＞ 字面，門沒關就不用撤」

### 5.2 看一段互動，不看單句

**定稿：**

> 一則訊息只能算線索。先看前後 3–5 則訊息、回覆是否持續、她有沒有主動補內容，再決定下一步。

所有綠／黃／紅燈與「回得熱／一般／冷」都要套用這條。

### 5.3 「測試」只是一種可能

**定稿：**

> 帶刺的問題可能是好奇、開玩笑、確認界線，也可能是不舒服。先看語氣與前後文，再決定直接回答、輕鬆接，或停下來確認。不是每個問題都是測試。

取代「她丟測試就代表認真考慮你」等必然推論。

### 5.4 邀約種子

**定稿：**

> 種子是先提一個具體活動，暫時不定時間，看看她想不想接。例如：「妳剛說那家咖啡店，我也想去。哪天一起。」她明確答應後，再在一到兩輪內敲時間。

因此：

- 「改天約妳喝杯咖啡」單獨出現仍太空泛。
- 「哪天帶妳去吃那間」只有在「那間」已經有共同上下文時才成立。
- 玩笑式邀約不是同意。

### 5.5 具體提案

**定稿：**

> 清楚說活動、時間與地點，再留一個好回答的確認口。例如：「週四晚上七點去那家店？妳可以的話，我就訂位。」

取代替對方直接決定的「週四晚上七點，我訂位」。

### 5.6 確認

**定稿：**

> 雙方已同意時間後，再簡短確認：「明天七點一號出口見；妳臨時有變再跟我說。」

不得把「沒有否認」或笑著反駁當成已答應見面。

### 5.7 被拒絕或取消

**定稿：**

> 她說不行，就先接受。她主動給另一個時間，就一起改期；沒有替代方案，就不要立刻再約。之後若互動仍然雙向，可以隔一段時間再看新的方向。

刪除「拒絕階梯」「拒絕要有成本」「下次奶茶妳請」整套規則。

### 5.8 回覆速度

**定稿：**

> 快回不是問題。長期回得比對方多很多、節奏完全繞著她轉，才可能失衡。忙就晚點回，想聊就正常聊，不用計時器。

與第 3 冊的「不要刻意操作回覆時間」完全一致。

### 5.9 爭執

**定稿：**

> 吵架不等於關係結束，也不能拿來證明她在乎。重點是能不能把問題說清楚、守住界線，再回到日常。

取代「她跟你吵，代表她還在乎」。

### 5.10 穩定與真實反應

**定稿：**

> 問題不是穩定，而是整段互動只剩附和，沒有真實反應。穩定可以保留，同時也要表達自己的偏好。

修正第 5、6 冊對「穩定／可預測」的衝突。

### 5.11 玩笑界線

**定稿：**

> 玩笑可以碰當下情境，不拿身體、外貌、家世等對方不容易改變的特徵當笑點。她沒接，就換方向。

因此刪除「跟妳一樣短腿」範例，改成：

> 「柯基吧，牠走路像趕著下班，很有喜感。」

## 6. 內容真源與匯入架構

### 6.1 現況

[tools/content/README.md](https://github.com/PoYuTsai/VibeSync/blob/ff17e04f9d26bf34564696bed575fa1d129611ab/tools/content/README.md) 明確寫著第 1–4 冊由外部夥伴 HTML 產生；[build_ebooks_from_guide.py](https://github.com/PoYuTsai/VibeSync/blob/ff17e04f9d26bf34564696bed575fa1d129611ab/tools/content/build_ebooks_from_guide.py) 目前會直接覆寫 assets 正式 JSON。原 HTML 與 bruce_nodes.json 又不在 repository。

如果開始直接手改 60 多段文案與大量 block 結構，但不改這個流程，下次有人重跑 builder，優化會整批消失。

### 6.2 最終建議：正式 JSON 成為產品真源

這次優化規模已超過「上游原文加幾個補丁」。建議做一次明確 cutover：

| 層 | 新責任 |
|---|---|
| 夥伴 HTML | 外部參考來源，不是 App 可直接覆寫的真源 |
| parse_partner_guide.py | 把新來源轉成臨時節點 |
| build_ebooks_from_guide.py | 產生匯入候選檔 |
| build/ebook_import_candidate/ | 比對區；不得由 App bundle 使用 |
| assets/learning/ebooks/book_1…book_7 | 唯一正式產品文案真源 |
| compare_ebook_import.py | 依穩定 ID 比對夥伴更新與正式內容 |
| audit_ebook_copy.py | 檢查正式內容的標點、長度、重複、術語與契約 |

### 6.3 builder 必須改成 fail-safe

- 預設輸出改到 build/ebook_import_candidate/。
- 若輸出路徑解析後位於 assets/learning/ebooks，預設直接失敗。
- 只有明確的 maintainer flag 才允許產生候選檔到指定路徑，但仍不得靜默覆寫正式檔。
- 產生完成後顯示新增、刪除、文字變動與 ID 變動摘要。
- source manifest 記錄來源版本、SHA-256、匯入日期與產生器版本；若授權不允許存原 HTML，只存 digest 與人工可辨識版本。
- README 改成「候選匯入 → 比對 → 人工合併 → audit → Flutter tests」，刪除直接覆寫正式 assets 的說明。

### 6.4 為什麼不把大型 override manifest 當預設

- 這次不是十幾個字串，而是標點、遺失標題、block type、跨冊規則與 60 多段改寫。
- 大型 override 會變成第二份難以閱讀的教材；reviewer 看到的是 patch，不是最後使用者看到的順序。
- 外部來源不在 CI，完整重建仍無法由 repository 自己重現。
- 正式 JSON 已有穩定 ID，適合直接做產品編輯與 diff。

只有在 Eric 確認夥伴 HTML 會高頻更新、且必須自動同步時，才改採「link_cross_refs 後、write 前套 typed override」的備案。備案必須有 expected old value／hash、未命中即失敗與完整生成 diff。

## 7. ADR 與拍板方式

[ADR #32](https://github.com/PoYuTsai/VibeSync/blob/ff17e04f9d26bf34564696bed575fa1d129611ab/docs/decisions.md) 的「內容一個字不改」是 2026-07-31 排版調整的範圍限制，不是永久禁止內容改善。這次仍應新增一筆 ADR，避免未來再次出現雙真源與規則漂移。

新 ADR 應記錄：

1. 本計劃是新的內容優化專案，明確擴充 ADR #32 當時只動排版的決定。
2. assets JSON 成為正式產品真源；夥伴轉換器降為候選匯入工具。
3. Eric 擁有產品語氣與跨冊規則的最終決策。
4. Bruce 校對第 1–4 冊是否保留原教學意圖；這不是讓每個標點都重新審批。
5. 第 5–7 冊可依本計劃直接做產品文案編輯。
6. P0 canonical rules 是跨冊契約，日後新增教材也必須遵守。
7. 純排版／標點不升 contentVersion；教學語意改變才升。

## 14. 進度、ID 與 contentVersion

[ebook_progress.dart](https://github.com/PoYuTsai/VibeSync/blob/ff17e04f9d26bf34564696bed575fa1d129611ab/lib/features/learning/domain/models/ebook_progress.dart) 已明確說明：contentVersionSeen 只記錄，不會清除完成章節或 checklist。真正保留進度的是 stable ID；quiz 由 quizRevision 控制。

因此最終策略是：

- 不改 book ID、chapter ID、entry ID 與 crossRef target ID。
- 同一教學點由 paragraph 改 comparison／checklist 時，能保留原 block ID 就保留。
- 新增 heading 使用穩定、可讀、以 ebook-N-cM- 開頭的 ID。
- 章名可改，不影響 resume，因為續讀存 chapter ID。
- 工作包 1–3 若只改標點與結構，不升 contentVersion。
- 工作包 4–6 完成後，對真正改變教學規則的書升版。依目前範圍建議：
  - 第 2 冊：3 → 4（R 定義）
  - 第 4 冊：3 → 4（邀約與拒絕）
  - 第 5 冊：1 → 2（7／38／55 與三軸）
  - 第 6 冊：1 → 2（爭執、穩定、回覆速度）
  - 第 7 冊：1 → 2（判讀、邀約與拒絕）
  - 第 1、3 冊若只改說法與結構，維持 3。
- 若任何 quiz 的正解或教學結論改變，另升該 quizRevision；不能只靠 contentVersion。

### 19.3 與計劃字面不同的實作決定

1. **builder 不提供「maintainer flag 寫入正式目錄」。** 計劃 6.3 說 flag 可以指定路徑但仍不得靜默覆寫；實作上「不靜默」最可靠的做法就是根本不寫——合併一律走 compare → 人工。若日後真的需要整份覆寫，那是一次有意識的檔案操作，不該由工具提供捷徑。
2. **長度以「不含空白的字元數」計**（R06），避免多行欄位的縮排與換行灌水；≥80／100／120 的規模統計則沿用計劃的「字元（含標點與空白）」口徑，所以 1,569／168／107／65 與第 2.1 節一致（總字元 49,674 vs 49,712 的差異來自 book／chapter 層欄位的計法，不影響門檻）。
3. **禁用詞「沒有否認」縮到「沒有否認「見面」」**：第 6 冊 2.2 的對話註解「沒有否認，沒有解釋，沒有慌」是接住測試的正確示範，泛用字串會誤殺。
4. **R13 定稿句用字串比對**，工作包 4 落地前 10 條缺漏記在 baseline；工作包 4 完成後這條會自然歸零，不需要改規則。
5. **你／妳角色規則暫不由 audit 自動判**：要判斷句子對象是使用者、女方還是泛指，需要 speaker 與敘述角色，機器判不準；列入工作包 2／5 的人工校對清單，audit 只守「一律訊號、一律鉤子、LINE」這類無歧義的一致性。
6. **R05 以「含「｜」的欄位」計 58 筆**（計劃的 70 是「｜」字元數），兩者指同一批表格殘留。
7. **R12 禁用詞清單多收了「假定同意」「假定式推進」「週四晚上七點，我訂位」「改天約妳喝杯咖啡」「下次奶茶妳請」**，直接對應第 5.4–5.7 節的取代規則，讓工作包 4 有明確的機器驗收點。
