### 最關鍵的一條鏈（失格→賦格→降階邀約）

```
她：「普通欸」「沒有很好」（酒量）
他：「那好像不能找你喝酒」「你會不會吐在我身上哈哈」   ← 失格
她：「我沒那麼遜ㄟ」「你不要灌我」「我就不會吐」        ← 她開始自我證明＝成功
他：「我不灌人酒」「破壞氣氛」「喝咖啡也可以哈哈」      ← 降階換場景
她：連發 5 則解釋咖啡因敏感                          ← 投入度爆表
```

以及「用否定讓她反收尾」：
「不想害你還是別約咖啡了」「約酒吧」→ 她反過來爭取「咖啡廳可以約啦」。

## 二、Eric 這輪的拍板（照時間序）

1. **字回太多** → 目標 20-40 → 12-28 → **8-20 字**，每則 2-15 字多數 4-10。
2. **「笑死」可以寫，不用怕** → 放行 2-5 字純情緒短則，至少一則 ≤6 字。
3. **女生要多顆球回**（模擬真實）→ NPC prompt 改成 1-3 則、則數由心情決定。
4. **hint 也可以分則** → 換行分則，UI 拆泡。
5. **中英夾雜比較接近真實** → 先全禁（錯）→ 只准專有名詞（還是錯）→ **全面放行**。
   Eric 的範例：「那間 bar 蠻 chill」「都一直躲酒 我有點 sad」。
6. **台語＋注音諧音** → 放行（歹勢／母湯／甘安捏／ㄏㄏ／ㄟ）。
7. **打字太快會打錯** → NPC 允許小錯字、注音沒選到。
8. **hint 不猜使用者喜好，給選項最穩** → 兩顆球各走一個立場。
9. **廢測不能硬回**（他主動提醒）→ 偵測器排除質問句形。
10. **不要技巧中毒，平聊占大多數** → 戰術從「規定動作」降為「方向」。
11. **雙向篩選**：立場不同也是價值，但要用敘事不是說教。
12. **對話不是永無止盡**：Game 要在有限回合走完流程到速約。
13. **必須瘦身** → prompt 7514 → 7039（後續補規則回到 7140）。
14. **最後一顆球不要寫死** → 依 server 算出的速約階梯分四種講法。
15. **短不等於空** → 補平衡規則。

## 三、實作上的關鍵決定（含為什麼）

### 分則：一則訊息、一個 turn、一次請求（做法 B）
UI 依換行拆成多顆泡（上限 4），但**本地仍是一筆 `PracticeMessage`、上行仍是一則
user turn、扣一次額度**。不可以改成迴圈送 N 次——本地索引會和 `request.turns`
索引錯開，而 `appliedHintTurns[].turnIndex` 是 debrief「你有照提示做」責任歸屬的鍵。

### 逐字稿的則界要保留但不能被抄
`flattenMultiBubbleText()` 把換行換成**引號包每一則**（`「對呀」「算是緣份」`）。
原本用「｜」分隔，離線重放實測**模型會把分隔符當輸出格式抄走**，產出
「追劇喔｜那妳會邊吃東西嗎」這種單則裡塞直線的句子。引號是內容標記不是分隔符。

### server 算得出來的就不要讓模型猜
- `partnerBubbleRhythmPrompt`：她這則發了幾顆球 → 給節奏建議
  （她 1 則→回 2-3 則帶節奏；**她 4 則以上→只回 1 則短的把節奏收回來**）
- `stanceOptionPrompt`：她在問你的喜好 → 注入「兩顆球各走一個立場」硬指令
- `lastHintPrompt`：最後一顆球 → **依速約階梯**給四種不同講法

**教訓**：規則寫在契約裡第 N 條會被前面十幾條稀釋。立場選項原本只是一行規則，
離線重放三個情境全部沒觸發、而且模型自己編了「我會潛水」這種使用者沒說過的事。
改成 server 偵測後注入硬指令才生效。

### 立場選項的標籤
`HintReply.label` 型別從寫死的兩個字串放寬成 `string`；模型可填
`warmUpLabel`/`steadyLabel`（2-6 字），**清洗失敗一律退回預設、絕不 throw**
（標籤只是卡片標題，不值得為它開 503 路徑）。client 本來就是 `Text(reply.label)`，
零改動。

### 廢測排除（Eric 提醒後補的）
`PARTNER_SHIT_TEST_QUESTION` 擋掉「每個女生／對誰都／很會講／編故事／套路／油／
想幹嘛／認真的嗎／在說什麼」。**硬給兩個認真的立場＝教使用者認真解釋自己，
比不給選項還糟。** 偵測矩陣 20/20 釘在 `hint_test.ts`。

## 四、踩到的坑（重複踩會很痛）

1. **守門會殺掉品質最好的候選**，而且看不出來——要 dump 被擋候選才知道。
   實例：「站到腿抖還打字，妳這反應有點讓人在意，我本來只想回一句的」（教科書級
   男女前提）被丟掉，只因為 coaching 漏寫「速約任務：」五個字。
2. **戰術行同時給兩個選項時，模型 100% 挑好寫的那個做。** 「男女前提／生活樣本」
   並列時男女前提整場長不出來。一行只給一個動作。
3. **中文沒有詞邊界**，邀約分類器連環誤判：
   - 「跟我**一樣**」被讀成「跟我一起」
   - 「看**來我這**關過了」命中「來我這（裡）」
   - 「跟妳**打**個招呼」命中「打（球）」
   - 「我們一起看片**大概會**搶遙控器」＝想像畫面被當成邀約
   全部修成負向前瞻／後顧，並加了假想語氣豁免。
4. **`厂` 是 `廠` 的簡體字**：台灣人打「厂厂」當笑聲會被 `toTraditionalChinese`
   轉成「廠廠」。prompt 要求打真注音 `ㄏㄏ`，已加測試釘住。
5. **模型偶爾把換行寫成字面 `\n`**：加 `normalizeLiteralNewlines()` 修復。
6. **`GAME_INVITE_ROUTE_ADVICE` 是雙用的**——它也會顯示在 fallback 卡的心法裡，
   禁令例句寫進去會漏給使用者看到。prompt-only 的規則要放 `speedInviteLadderPrompt`。
7. **瘦身時別刪「骨架 P1→P5」**：那是 hint／NPC／debrief 三個介面的對齊不變量，
   有測試釘死。
8. **提高守門召回會讓首發更常被擋**（Eric 明確否決）。漏判的邀約句形改在
   **prompt 端讓模型不產出**，不動守門。

## 六、第二輪離線黑箱（同日稍晚）——修掉三件、語料總對照

模擬器先補了三處 production 保真度才跑（前一輪的結論有一部分是儀器造成的）：
溫度判定改走 `buildTurnClassifierMessages`→`parseTurnClassification`→
`applyLearningClassification`（舊版走 `buildTemperatureJudgeMessages`，拿不到 mood）；
`partnerMood` 真的會動（修復優先路徑前一輪等於沒測過）；階梯顯示補上 `inviteStage`。

### 修掉的三件

1. **速約階梯被 ledger 蓋回「不約」（真 bug，可執行證明）**
   `handler` 落帳的 `evaluateGameFsm` 漏帶 `inviteStage` → ledger 記下
   `no_invite_build_investment` → `effectiveGameFsmSnapshot` 在非修復優先時
   拿 ledger 的值蓋掉 fresh。結果 `soft_invite_probe`／
   `direct_invite_low_pressure`／`partner_window_close` 在順風局 **100% 走不到**，
   最後一顆球的四種講法只有「鋪墊版」出得來。實測溫度 70／熟悉 60
   （成熟度 66＝可直接邀約）進 prompt 的仍是「這輪不約」。
   收斂成單一入口 `evaluateGameFsmForLedger()`，測試釘在 `game_state_test.ts`。
   修後 8 球局四段階梯全部走到：no_invite → soft_invite_probe(50) →
   direct_invite_low_pressure(72) → partner_window_close(84)，phase 也第一次到 P5_CLOSE。

2. **立場選項標籤從來沒填過**（4 場 7 次觸發、0 次填）
   真因是同一件事被講了三遍而且互相打架：`sevenStepBalanceContract` 說必填、
   後半句又說「一般情況這兩欄留空即可」，tool schema 兩個 label 的 description
   也說「一般情況留空」。模型照慣例挑好寫的那條走（同坑 #2）。
   改法：always-on 契約只留原則、標籤機制交給 server 偵測後注入的
   `stanceOptionPrompt`；schema description 改成「不同立場時必填」。修後第一次填出
   〔沒特定地點〕／〔也懂那感覺〕、〔帶點調侃〕／〔體貼收〕。

3. **心法超出 140 軟上限 8/19（最長 257 字）**
   契約要六個要素塞進 140 字，本來就不可能。改成「全文 140 字以內、就寫三句」
   （階段＋任務／原因／速約任務）。修後中位 137→105、超標 10/24→1/19。

### 承瑋 22 張截圖總對照（逐字稿：`tools/voice-benchmark/chengwei-transcript-draft.md`）

他自己發的 88 則：**中位 7 字、平均 7.9、≤6 字佔 45%、20% 帶問句**。
我們字長早就對上了（中位 7、平均 7.6、≤6 字 40%）。**差別全在短則裡裝什麼**：

- 他的 40 則短句：`我是水男孩｜溫泉也可以｜調酒不好喝｜我不灌人酒｜樂華錢櫃｜
  我在中壢｜看來你不花心｜沒啥興趣｜都去青埔哪裡｜那你酒量如何｜要組隊了嗎｜
  需要導遊嗎`——給自己的事實、給立場、或把局往前推。純情緒只有 5 則（12%）。
- 我們的 45 則短句約 **62% 是空的**：回聲（她說站一整天→「站整天真的累」）、
  安撫（辛苦了／先休息／慢慢來就好）、空泛問候（今天過得如何）。
  **承瑋 88 則裡一句安撫語都沒有。**

原本的「短不等於空」規則禁的是「還好啊／普普通通／就那樣」這種字面模板，
跟實際的空句型態不一樣，所以形同虛設。

**第一次改（失敗，已放棄）**：規則改成「每一則都要帶東西」＋正面例句。
同條件重測（B 場前 6 輪）中位 7→8、≤6 字 48%→32%——模型用**加字**來讓句子有料，
反而離語料更遠（承瑋 45%）。

**第二次改（留下）**：直接點名最省字的兩種內容（**自己的事實**／**推進的短問**）＋
點名三種空句型態，並明說「用加字來讓句子有料就搞反了」。

同條件重測（B 場 6 輪，n=24 則）：**短則的內容型態明顯對齊語料**——

### 這輪新確認的坑

9. **改 prompt 規則要同條件重測，不能只看有沒有變好。**「要帶東西」這種正向要求
   模型會用加字達成；要省字就得直接指定省字的內容型態。
10. **離線模擬器改動要跟著 production 一起改。** 修好 handler 落帳後第一次重跑
    階梯還是不動——因為 sim 自己的落帳還在呼叫舊路徑，白跑一場。
11. **禁「安撫語」跟修復優先的戰術方向直接打架**（`gameTacticDirectiveFor` 的
    「她退你就退一步：降壓、接住她保留的點」＋「先讀淺溝通：累→降成本」）。
    方向句比契約條文強，「辛苦了」照樣出得來。承瑋在對方退的時候做的是
    幽默接住＋失格（「那好像不能找你喝酒」），不是安撫——**修復戰術本身要不要
    改成語料的做法，是產品決定，未動。**
