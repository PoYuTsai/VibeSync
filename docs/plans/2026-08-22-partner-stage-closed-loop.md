# 對象卡互動階段閉環

## 一句規則

每次成功分析，都替該對象寫入一個「本次互動階段」快照；作戰板永遠顯示最新快照，從未成功分析才顯示問號，任何缺值或壞資料都不得假裝成破冰。

## 使用者要看到的六種狀態

| 畫面 | 內部值 | 本次互動的判讀 |
|---|---|---|
| 問號 | 無 stage snapshot | 對象卡已建立，但從未有成功且有效的 AnalyzeChat 階段結果 |
| 冰塊 | `opening` | 真正初次開場；或任何關係在有明確沉寂、失聯、修復等證據後重新接軌。伴侶文案必須說「重新連線」，不能暗示退回陌生人 |
| 火焰 | `premise` | 已超過普通朋友聊天，正在建立男女感、曖昧張力或彼此個人好奇 |
| 天秤 | `qualification` | 正在互相確認價值觀、界線、生活節奏、投入程度或關係期待是否合適 |
| 盔甲 | `narrative` | 正在透過個人故事、情緒、身份與生活樣本深化理解與連結 |
| 邀約物件 | `close` | 對話存在真實邀約窗口、提議、接受、改期或時間地點等可落地證據，適合推進下一個具體安排 |

`normal`、`stuckFriend`、`canAdvance`、`shouldRetreat` 是階段內的節奏狀態，不選 3D 圖。可見文案使用「維持節奏／互動偏平／可以推進／放慢一點」；伴侶不得出現「朋友區」或「偏朋友」字樣。

## 三條彼此獨立的產品真相

1. **本次投入度**回答「她在最新分析片段裡花了多少心力參與」，不回答她多喜歡使用者。
2. **目前互動重點**回答「下一句最需要完成哪一種互動任務」，不回答整段關係升到第幾級。
3. **關係與情境背景**回答「兩人從哪裡出發、認識多久、目前目標與已知限制」，只能協助解讀，不能直接加分或指定階段。

畫面原本的「對話進度」改成「目前互動重點」。五個點只凸顯本次焦點；不得把較早的點全部畫成已完成成就。典型順序仍可作教練參考，但 premise／qualification／narrative 可以反覆切換，close 之後也可以回到其他互動任務。

## 本次投入度

### 定義與分段

- 0–30：這次投入偏少。
- 31–60：有回應，但仍需觀察。
- 61–80：投入訊號明顯。
- 81–90：高度主動參與。

只評最新分析片段中「她」可觀察到的行為：具體內容、獨立球數、主動提問、延伸、callback、自我揭露、情緒具體度、邀約窗口與互惠程度。使用者自己寫很多、單顆 emoji、單次慢回、手動勾選的背景都不能加分。回覆速度只有在輸入真的存在可信的多輪時間證據時才可作低權重訊號。

長篇拒絕或清楚設界線可以代表她有花心力表達，但仍可能是 No-Go；投入度、浪漫興趣與是否值得繼續投入必須分開。前一次分數只用來顯示趨勢，不參與本次分數。保留既有且已拍板的 finalize `× 0.9` 產品校準：模型內部仍以 0–100 判讀，使用者可見尺度正式定義為 0–90，raw 100 顯示 90。所有圓環、分母、文案與分段都必須以 90 為滿分，不能一邊顯示 `/100` 一邊永遠只到 90。

## AnalyzeChat 選擇階段的方式

先處理安全、拒絕、界線、第三方與 No-Go，再從最新一輪對方訊息判斷「下一句最需要處理的主要未解任務」。整段歷史、上次有效階段與情境只協助消歧，不得蓋過最新證據。

1. 有本輪仍有效的共同活動／見面／通話窗口，且對方有提議、接受、改期、追問時間地點等互惠證據 → `close`。
2. 核心是感情目的、價值觀、界線、生活節奏、距離、標準或適配度，且不是使用者單方面查戶口 → `qualification`。
3. 核心是個人故事、感受、身份、經歷、脆弱面或生活樣本，下一步應接住並深化理解 → `narrative`。
4. 核心是雙向互虧、曖昧、關係化語言、玩笑試探或彼此個人好奇，且對方有接住 → `premise`。
5. 其餘屬剛開始建立回覆通道，或有明確沉寂／失聯／衝突後正重新接上 → `opening`；伴侶顯示「重新連線」。

多種證據同時存在時，不以歷史最高階段決定，而以最新未解任務為主；具體共同安排優先於它所依附的話題，明確適配／界線問題優先於一般故事。只有舊對話曾約過、使用者單方面邀約、目標勾「邀約見面」或關係勾「已是伴侶」，都不能形成 `close`。

## 判讀規則

1. 一次成功分析恰好產生一個有效 stage snapshot；判的是「這次互動現在最適合做什麼」，不是替整段關係永久升級。
2. 同一對象第 2、3、4 次分析可以換圖。階段不是單向解鎖，也不保留「歷史最高級」；最新成功分析才是作戰板真相。
3. 往前或往後移代表戰術焦點改變，不等於感情變好或變差。例如邀約被婉拒後，下一次可能回到建立男女感或互相評估。
4. `opening` 必須有正面證據：真正第一次接觸，或明確沉寂、失聯、衝突後正在重新建立互動。單次短回、普通問候、模型缺欄位、未知字串都不能讓既有快照變成冰塊。
5. `已是伴侶` 不會因一則冷回就判成 `opening`；只有本輪確實在重新接軌時才可使用同一內部值，且可見語意固定為「重新連線」，不是關係清零。
6. `close` 不由「已是伴侶」或使用者目標「邀約見面」直接觸發；必須從本次訊息看見可推進的邀約或安排證據。
7. `narrative` 不是中間預設值；只有真的存在故事、情緒、身份或生活樣本深化連結時才能選。
8. 前一次 stage、認識情境與對象歷史是連續性證據，但不能鎖死本次判讀；本次訊息仍是主要證據。
9. AI 缺少、寫錯或輸出無法映射的 stage 時，本次不得寫入新快照；保留上一個有效階段。若從未有有效階段，維持問號。

## 跨次分析與回退

- 上次有效階段是弱先驗，不是下限；必須隨下一個 partner-bound 分析片段送入 AnalyzeChat。
- 強證據可以直接跳階；不要求依序走完五個點。
- 一次短回或冷回只降低本次投入度並可標 `shouldRetreat`，不能單獨把既有階段重設成 opening。
- 邀約被放掉後可回 premise／qualification／narrative；這表示戰術焦點改變，不是關係退步。
- 同一內容修訂的重試／重新整理只更新同一次分析，不新增趨勢事件；新訊息內容修訂才新增快照。
- 新分析失敗或 stage 非法時保留前一個有效快照。
- 真正把較舊截圖延後匯入時，現有 OCR 沒有可信的原始對話日期；本版明示以成功分析順序當時間順序，不假裝已解決。未來若要支援倒序匯入，需另加「舊對話／對話日期」輸入。

## 資料閉環

```text
一批截圖／訊息
  → AnalyzeChat 依本次內容＋認識情境＋對象歷史選一個 stage
  → 僅在完整分析成功且 stage 有效時寫入 stage snapshot
  → snapshot 綁定 partnerId 與分析完成時間
  → 作戰板按分析完成時間取該對象最新有效 snapshot
  → 映射成對應 3D 圖；完全沒有 snapshot 才映射問號
```

### 既有資料相容

- 新的 append-only `AnalysisHistoryEvent.analyze` 是最新階段的優先來源，使用 `createdAt` 排序。
- 舊資料若沒有 history event，可從 Conversation 的有效分析快照／`currentGameStage` 做 legacy fallback。
- legacy fallback 只接受五個合法值；未知值不准透過 `GameStage.fromString` 默認成 opening。
- 修改對象卡的認識情境後，新分析片段必須取得最新對象設定；既有非空 `SessionContext` 不得靜默擋住新的 `meetingContext`／`duration`／`goal`。

### 情境與 chips 的影響邊界

- `meetingContext`（交友軟體／現實認識／朋友介紹／已是伴侶）與 `duration` 只校準起點、信任與推進速度；不直接指定 stage 或分數。
- `goal`（邀約見面／維持熱度／自然聊天）只調整建議方向；勾邀約不能強迫 `close`，勾自然聊天也不能隱藏對方主動提出的邀約窗口。
- 本次補充背景可解開「男友指誰」「是否已約好」等當前事實歧義，但不得覆蓋對方明確拒絕、安全、同意或界線。
- 「關於她」六組 allowlisted chips 可調整節奏、話題、管道、時間與邀約可行性；不可直接改分、改 stage、偽造為她本輪原話或替連續低投入找藉口。互斥與各組上限繼續由 catalog 守門。
- 「關於我」不進 AnalyzeChat 的投入度、stage 或五風格判讀。現有 stuck points／practice goals／notes 只供 Coach 1:1；topic seeds／custom topics 目前不進 AnalyzeChat。畫面文案必須說清楚，不得再宣稱所有項目會直接幫 AnalyzeChat 發想。
- 舊分析片段保留當時 context，不能被今天修改的關係設定改寫歷史；新片段必須使用對象卡最新 defaults。

## 實作範圍

1. **分類契約**：強化 AnalyzeChat system/stream prompt 的五階段判準、最新片段優先、上次階段弱先驗、chips 邊界與 opening guard；不得呼叫付費模型做驗證。
2. **輸出守門**：缺少或非法 stage 不能變成 `opening`，也不能覆蓋上一筆有效 snapshot；不得改壞既有 quota／retry 的 exactly-once 語意。
3. **情境接線**：修正 partner-bound 新片段／截圖匯入，確保「已是伴侶」等最新設定真的送進下一次分析。
4. **作戰板真相**：優先用最新成功的 partner-scoped history event 取 stage，Conversation 僅作 legacy fallback；不得用普通 `updatedAt` 把舊分析誤當最新。
5. **無額度預覽**：提供不呼叫 AnalyzeChat 的六狀態預覽 seam，能一次看見問號與五張 stage 圖；不得把測試入口暴露成一般正式功能。
6. **領域文件**：實作不得違反根目錄 `CONTEXT.md` 的詞義。
7. **結果畫面**：把「對話進度」改為「目前互動重點」，只凸顯本次 stage，並顯示節奏狀態；`stuckFriend` 對使用者顯示「互動偏平」。
8. **投入度尺度**：保留 finalize `× 0.9`，正式把可見滿分定義為 90；由固定 fixture 鎖定顯示值 0／30／31／60／61／80／81／90 的合法邊界，圓環與任何可見分母同樣以 90 為滿分；不得呼叫真實模型。
9. **關於我文案**：文案與實際接線一致；不在本案把 About Me 重新接入 AnalyzeChat。

## 已確認的測試 seams

這些 seams 由 Eric 的「照建議處理」承接前一輪提案，視為已確認：

1. **Edge 分類契約 seam**：給 prompt builder／stream reframer 固定輸入，驗證五階段判準存在、合法 stage 可通過、缺值／非法值不會成為 opening。
2. **Flutter 完成分析 seam**：用一個成功 `AnalysisResult` 經公開 persistence coordinator，驗證 partnerId、stage 與完成時間形成可讀的最新快照；失敗或非法結果不覆蓋舊值。
3. **報告作戰板 seam**：用多個 partner-scoped history events 與 legacy conversations，驗證每個對象只取最新有效分析、未知值顯示問號、一般 Conversation 更新不改寫階段順序。
4. **情境 seam**：從對象卡最新設定建立下一個分析片段，驗證 committedPartner 不被舊 Conversation context 吃掉，且 request payload 實際送出 `已是伴侶`。
5. **資產預覽 seam**：一個測試／開發入口一次渲染六個狀態，逐一斷言正確 asset path 與可見標籤，全程不呼叫 AI。
6. **投入度 seam**：固定 raw score 通過 finalize，驗證既有九折校準、合法範圍 clamp、raw 100 → visible 90，且四個 UI 分段與滿圈邊界一致。
7. **互動重點 seam**：公開 widget 驗證只有目前 stage 被凸顯、狀態文案可見、畫面不把前段畫成已完成。
8. **跨次連續性 seam**：第二片段送出前能取得上一個 partner-scoped 有效 stage；模糊證據保留弱先驗，明確新證據可前進或回退。
9. **About Me seam**：buildForAnalysis 仍為 null；UI 不再宣稱 topic chips 會直接影響 AnalyzeChat。

## TDD 與驗證要求

- 每個垂直切片先出會失敗的行為測試，再做最小修改轉綠；不要先一次寫完所有測試。
- 優先測公開 seam，不 mock 專案內部 class；外部 AI／資料庫邊界可用固定 fixture。
- 執行最小目標測試後，再依環境契約於 WSL 執行相關 analyze／較寬測試。
- 不呼叫真實 Anthropic／Supabase production，不 push、不部署、不開 PR。
- 最後精準 commit 任務檔案，回報 commit SHA、變更檔案、測試命令與任何未解風險，交由 Codex 主審。

## 驗收案例

1. 新對象卡、零成功分析 → 問號與「尚未分析」。
2. 同一對象依序得到 premise、qualification、close → 作戰板依序換成火焰、天秤、邀約圖，不保留歷史最高或第一張圖。
3. 同一對象最新分析從 close 回到 qualification → 顯示天秤；文案不得暗示關係退步。
4. 已是伴侶＋單次短回或一般生活訊息 → 不得只因內容短就覆蓋舊 stage 成冰塊；依本輪主要任務與弱先驗判斷。
5. 任一關係有明確沉寂／失聯／衝突後重新開場 → 可以顯示冰塊；伴侶可見文案是「重新連線」，不是關係清零。
6. 已是伴侶＋「週六兩點去那間咖啡店？」「好」 → 可以顯示 close，因為有本次安排證據，不是因為伴侶標籤。
7. stage 缺失、`vibing hard` 或其他未知值 → 不得顯示冰塊；有舊快照就保留舊圖，沒有就問號。
8. 對 Conversation 只改名字或其他普通欄位 → 不得讓它超車較新的分析事件。
9. 在對象卡把認識情境改成已是伴侶後建立下一片段 → Edge request 收到 `meetingContext: 已是伴侶`。
10. 六狀態預覽 → 六張資產都能載入，且零網路／零模型呼叫。
11. 用戶單方面邀約、她沒接 → 不得判 close；若前次為 close，可回到適合的 stage 並標放慢。
12. 她主動問感情目的／抽菸／距離／生活方式 → 可直接 qualification，不要求先 premise。
13. 雙方互虧且她接住關係化玩笑 → premise；只有用戶單方面撩、她禮貌回覆 → 不得 premise。
14. 她分享個人挫折／情緒／經歷，下一步應理解而非排程 → narrative；一般一句行程更新不得自動 narrative。
15. raw score 100 經 finalize 顯示 90 且圓環為滿圈；顯示值 30／31、60／61、80／81 分別落在正確四段，任何使用者可見文案不得寫 `/100`。
16. 同一 content revision 重跑 → 不新增第二筆趨勢；新增訊息後成功分析才新增。
17. 關於她勾「慢熱／工作忙」不能提高本次投入度或替低回覆改 stage；只可讓建議降壓或調整時間。
18. 關於我勾任何卡點、目標或話題 → 不改投入度與 stage；AnalyzeChat request 不帶 effectiveStyleContext。
