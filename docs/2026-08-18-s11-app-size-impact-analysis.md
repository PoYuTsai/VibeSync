# S11「App 體積」對 VibeSync 的影響分析（2026-08-18）

> 對象：`DESIGN.md` §9 已知債清單最後一列 —— `S11 自訂繁中字體｜拍板暫緩（App 體積），上架穩定後再議`。
> 目的：把「App 體積」這個否決理由攤成可查證的數字，判斷它擋得對不對、擋的是不是該擋的東西。
> 性質：純分析，未改任何 runtime 程式碼或設定。

## 0. 一句話結論

**體積這個理由本身站得住，但它擋錯了對象。** 真正吃掉體積的是已經在包裡的 23 MB 圖片（占 IPA 四成），不是還沒加的字體；
而 S11 真正的風險也不是體積，是**度量位移**會把 B5–B8 剛收斂完的字級／間距憲法整個震開。
把 S11 拆成「標題專用顯示字（<200 KB）」與「內文字體（10–25 MB）」兩件事之後，前者的體積理由直接消失，後者的理由則從「體積」換成「度量與混排」——那才是該寫進拍板紀錄的真正理由。

### 1.2 目前字體成本 = 0

- `pubspec.yaml` **沒有 `fonts:` 區塊**，全庫 `fontFamily` 只有 2 處，且都是 `analysis_screen.dart` 的 `'monospace'`。

  S11 不是「換字體」，是「從零加一份字體進來」——增量就是全額。

- 也就是：S11 的否決理由從未被量化過。本文的數字是第一份。

## 2. 若照 S11 原案做（內文換自訂繁中字），體積代價是多少

繁中字體檔案大小（量級估算，實際要以選定檔案實測為準）：

| 方案 | 體積 | IPA 變化 | 增幅 |
|---|---|---|---|
| 全字重 ×3（Regular/Medium/Bold），未子集 | ~25–30 MB | 57 → **82–87 MB** | **+44–53%** |
| 可變字體單檔（如 Noto Sans TC variable） | ~10–12 MB | 57 → **67–69 MB** | +19–21% |
| 子集化至 ~6,000 常用字 ×3 字重 | ~9–12 MB | 57 → **66–69 MB** | +16–21% |
| **標題／儀式專用顯示字（數百字子集、單字重）** | **<200 KB** | 57 → **57.2 MB** | **+0.4%** |

依據：繁中字體單一字重約 8–10 MB（Big5 常用 5,401 ＋ 次常用 7,652 ≈ 13,000 字，CJK 字形平均約 500 B/字）；
子集到 6,000 常用字約 2.5–4 MB/字重。

## 3. 體積在 VibeSync 的實際約束力——哪些是真的，哪些是誤解

**不成立的擔心：**

- **App Review 沒有體積門檻。** 57 MB 或 85 MB 都不會被拒。S11 寫「上架穩定後再議」隱含「體積不是審核阻擋」，這個判斷是對的。
- **蜂巢下載限制碰不到。** Apple 的 OTA 上限自 2019 年起是 200 MB，且 iOS 13 起使用者可手動略過。57 → 85 MB 離線很遠。
- **TestFlight 不受影響。**

**成立但被高估的擔心：**

- **安裝轉換率。** 體積確實與安裝完成率負相關，但在 50–90 MB 這個區間、面對台灣 iPhone 用戶（機況與儲存空間普遍不差），彈性很弱。這不是「不能加 25 MB」的等級，是「加 25 MB 要換到對等價值」的等級。

**真正成立、但沒被寫下來的理由（見 §4）：** 度量位移與混排失控。

## 4. S11 真正的風險不是體積

### 4.1 度量位移會震開剛收斂完的憲法

`DESIGN.md` §3–§5 的字級（12/15/19/24/30/38）、間距（4/8/16/32）、行高節奏，是 B5–B8 在 **PingFang TC 的度量**下調出來的，涉及 547 處間距與 234 處圓角的收斂。
換內文字體＝換 x-height、換字面率、換預設行高 → 全 App 垂直節奏位移，`analysis_screen.dart` 這種已知的出格重災區首當其衝。
`docs/bug-log.md` 已有「較大字體時方案卡右側被截斷」的前例，代表這個 App 的版面對字體度量是敏感的。

代價不是 25 MB，是**再跑一輪 B5–B8 等級的全庫重調**，外加 §10 要求的全套改前／改後 PNG 對照。

### 4.2 子集化在 VibeSync 特別危險

一般 App 可以靠子集化把 9 MB 壓到 3 MB。VibeSync 不行，因為它**大量顯示使用者內容**：
OCR 出來的對話截圖、對象名字、使用者自己打的字、AI 生成的回覆。

缺字時 Flutter 會 fallback 到系統字——**不會出豆腐字，但會在同一句話裡混排兩種字體**。
台灣人名罕用字（堃、甯、頎…）、注音符號、混入的日文假名都會踩到。
在聊天泡泡和對象名這種最高曝光的介面上，混排比「整齊地統一用 PingFang」**更醜**。
所以子集化這條省體積的路，在 VibeSync 的內文場景上是關的。

### 4.3 在 iOS 上，自訂字要先贏過 PingFang

PingFang TC 是 Apple 專為中文設計的高品質介面字。主流開源繁中字（Noto Sans TC／思源黑體同一骨架）在 UI 級字級下不見得贏它。
Android 端預設本來就是 Noto Sans CJK——**bundle 一份 Noto 進去等於花 10 MB 買一個使用者本來就有的東西**。
換句話說：內文字體的品牌收益，在兩個平台上都比直覺中小。

## 5. 反過來說：目前「控制體積」的做法有隱形代價

這條線目前是**無預算、無量測、無 gate 的口頭約束**，典型失效模式已經發生了：

- **它只擋新東西，不管既有的。** 字體（0 → 10 MB）被擋下來；同時 5 張 Sydney PNG 吃掉 5.2 MB、100 張角色圖吃掉 12 MB，從沒被檢視過。
- **它把「體積」變成否決權，而不是可交易的預算。** 沒有數字，就沒辦法回答「這 10 MB 值不值」，只能一律說不。
- **順手發現的浪費：** `font_awesome_flutter` 宣告在 `pubspec.yaml`，但 `lib/` 內 **0 處使用**（`cupertino_icons` 同樣 0 處）。release 有 icon tree-shaking，實際浪費不大，但這是「沒人在看」的直接證據。

### 5.1 不動產品就能回收的體積

| 動作 | 預估回收 | 風險 |
|---|---|---|
| Sydney 5 張 PNG → WebP（帶 alpha） | ~3.9 MB | 低。解析度本身是合理的（顯示上限約 480 logical px 高，3x = 1440 px，對上 941×1672 沒有過度），**成本在格式不在尺寸** |
| 抽卡卡背 2 張 PNG → WebP | ~1.2 MB | 低 |
| 100 張角色圖重壓（統一 1080 高、q75） | ~3–4 MB | 低—中，需目檢抽樣 |
| 清掉未使用的 `font_awesome_flutter` / `cupertino_icons` | 極小 | 低 |
| **合計** | **~8–9 MB** | |

**回收 8–9 MB，就足以「付」掉一個可變字體的大半，或覆蓋標題子集方案四十倍以上。**
另外全庫只有 6 處用了 `cacheWidth`/`cacheHeight`/`ResizeImage`——這不影響 IPA 大小，但影響 runtime 記憶體，是另一條值得看的線。

## 6. 建議

### 6.1 把 S11 拆成兩件事（核心建議）

| | S11-A：標題／儀式顯示字 | S11-B：內文字體 |
|---|---|---|
| 用在哪 | 品牌 wordmark、hero 標題、區塊標題、儀式時刻（§3 的 24/30/38 級） | 全 App 內文（15 級） |
| 文案來源 | **App 自撰、固定字串** | 大量使用者內容 |
| 子集 | 可以，數百字即可 | 不可（見 §4.2） |
| 體積 | **<200 KB（+0.4%）** | 10–25 MB（+19–44%） |
| 憲法衝擊 | 只碰 3 個字級，改前／改後對照圖只需數個畫面 | 全庫垂直節奏重調，等同再跑一輪 B5–B8 |
| 建議 | **體積理由不成立，可以做** | 維持暫緩，但**理由改寫成度量與混排，不是體積** |

實作紀律：S11-A 的字只掛在**不插值使用者資料**的文字槽上（用 `AppTypography` 開一個專用 style），任何會帶進對象名／使用者輸入的標題一律不用。

順帶好處：一旦 App 自己帶字體，`test/visual_proof/` 的 golden 就不再依賴 CI 去裝 msjh（`distribute.yml` 目前有一步 `Install Traditional Chinese visual-test font`），跨平台截圖穩定性反而變好。

### 6.2 把「體積」從否決權換成預算

1. 在 `distribute.yml` 加一步記錄 IPA 大小（單行 `ls -l` 即可），讓每次 build 都有數字。
2. 訂一個明確上限（建議 **IPA ≤ 65 MB**，對現況 57 MB 留約 8 MB 餘裕），超過就要拍板，而不是靠印象否決。
3. 先做 §5.1 的圖片回收，把餘裕從 8 MB 拉到 16 MB，之後任何體積討論都變成「有預算可花」。

### 6.3 更新 `DESIGN.md` §9 的那一行

現行文字把「體積」當成 S11 的唯一理由，而本文顯示這個理由對 S11-A 不成立、對 S11-B 也不是主因。建議改寫時明確分成 A/B 兩列，並把 B 的理由寫成「度量位移＋使用者內容混排」。
