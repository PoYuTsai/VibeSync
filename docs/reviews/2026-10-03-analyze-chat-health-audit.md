## 0. 背景與方法

**為什麼做。** 對話分析是 VibeSync 的主力功能之一。Eric 在 2026-10-03 要求對它做一次全面健檢：模組會不會太重、輸入輸出、串流與等待畫面、品質，以及 prompt「感覺拼湊了很多」；要提出品質、效能、穩定性的優化建議，以及如果要動結構刀會怎麼提案。同時要從三個視角（第三方產品專家、Sydney 教練、用戶）判斷這塊有沒有價值、能不能做到市場最好，並看跟開場救星、新話題有哪些元件可以共用。

Bruce 的原話回饋：

> 目前是還可以，但等有點久，品質也還可，但也是很怕這個超大 prompt／技術債很難改，無從下手，怕有 regression。

**範圍。** 對話分析的後端程式（`supabase/functions/analyze-chat/`，與開場救星、新話題共用同一支 Edge Function）、App 分析頁（`lib/features/analysis/`）、實際送出的 prompt、黑箱評測工具與它存下的真實模型輸出（`tools/analyze-v2-blackbox/out/2026-10-02-*`），並對照開場救星、新話題與教練的做法。基準是 `main` @ `9adbf87c`。

**方法。** 全程唯讀，由 Claude Code 的多審查員流程完成：

1. 9 位技術審查員各看一塊：架構與模組重量、伺服器串流與延遲、App 等待畫面、prompt、輸入整理、輸出後處理、扣費與穩定、測試與防退步、跨功能共用。
2. 3 位產品評審：第三方產品顧問（含上網查競品）、Sydney 教練（逐案讀黑箱真實輸出）、目標用戶（照 App 實際流程走一遍）。
3. 每條 P1、P2 發現再派另一位審查員試著推翻：共 95 次核實，16 條完全成立、79 條方向成立但說法被修正、0 條被推翻；合併重複後得到 51 條（附錄 A）。
4. 三套結構刀方案（先建安全網、先拉品質、先縮短等待）由兩位評審分別用維護者與產品負責人角度打分並合成。
5. 報告初稿再由檢查員逐項對照來源，修掉沒有根據的數字後定稿。

**限制。** 沒有查 production、沒有呼叫付費模型、沒有真機測試。品質結論來自已存下的 23–42 案黑箱輸出；所有審查員與受評的模型都是 Claude 家族，這份報告本身沒有經過跨家族主審。附錄保留審查員原文，數字與本文不一致時以本文為準（例如附錄裡「約六成可原封送出」，本文已更正為「約七到八成」）。

**決策歸屬（Eric 2026-10-03 更新）。** 本文原本寫給 Eric，文中的「你」指 Eric。Eric 決定：**產品層的決定交給 Bruce 依他的品味判斷**，並請 Bruce 判斷、分析、實作、驗證後交付回來審。動到付費、額度、CI／部署設定、正式資料、付費評測預算與開關設定的部分，仍需要 Eric 點頭。實際分工以 Bruce 白話版為準。

這次對對話分析後端（analyze-chat）只做了唯讀稽核：沒有改檔，沒有 commit、push 或部署，沒有呼叫付費模型，也沒有查 production。本機只用 `deno --deny-net`（禁止連網）跑了既有測試。文中的「完成事件」是伺服器最後送出的「分析完成」訊號，App 收到它之後，結果才能操作。

## 1. 結論與你要決定的事

對話分析值得當主力功能。「要不要回」的判斷已經到教練等級，問題出在兩個地方：
- **「等有點久」主要是 App 的設計造成的。** 推薦卡約 8.5 秒就到了，App 卻要等完成事件（約 19 秒）才讓人複製。
- **「怕改」有具體原因。** CI 只跑約兩成測試，部署前一個後端測試都不跑，prompt 又被約 300 句逐字照抄 prompt 的測試綁住。

建議的順序是：先建安全網，再讓第一張卡一到就能複製，最後才拆 prompt。

**模組重不重：重。** 規模如下：
- 後端有 94 個原始檔、31,334 行。
- 一支 Edge Function 處理 9 種請求形狀，每種請求都載入 107 個本地模組。
- 主函式有 2,077 行，App 的分析畫面有 4,360 行。

但現在不要拆成多支 Edge Function。部署流程本來就會重部署全部通用函式，拆開並不會縮小影響範圍，只會讓閘門程式多出好幾份。應該沿著現有的切分點，在內部把模組抽出來。

| # | 要決定的事 | 預設 | 風險 | 不同意的後果 |
|---|---|---|---|---|
| 1 | 授權修改 `flutter-ci.yml` 和 `deploy-edge-function.yml`：整個目錄都跑測試和型別檢查，部署前先跑測試。 | 同意 | R2。只要有測試失敗，全部 8 支通用函式都無法部署，緊急修正也得先修好測試或還原。 | 改壞的程式仍可能通過 CI 上線，之後的重構都沒有安全網。 |
| 2 | 推薦卡一到就能複製，並且「送出即定稿」：用戶看過的卡，完成時不再被改寫或換成罐頭句。你 2026-08-17 定的「各卡段數相同」照舊保留，只是改在送出時就裁切。 | 同意 | R2。會動到和扣費順序有關的伺服器模組。 | 用戶每次多等約 10 秒，卡片偶爾會在完成時突然變掉。 |
| 3 | 她問到用戶本人的事（工作、照片在哪拍、推薦什麼）時怎麼處理。 | 卡片留「［你的工作］」這種空格，用戶填好才能複製；不重新啟用「關於我」。 | R2。要改 prompt 和 App，並用付費黑箱驗證。 | 照用戶視角的估計，需要回覆的分析大約每 4 次就有 1 次給出編造或閃躲的句子。 |

## 2. 價值判斷：三個視角

以下分數是模型扮演各個視角給的主觀評分，評審和受評的模型又是同一家族，只能當方向參考。

| 視角 | 結論 | 最在意的事 |
|---|---|---|
| 第三方產品顧問 | 有價值，但沒經過市場驗證（市場驗證 2/10，日後好不好擴充 4/10）。真正的對手是免費的 ChatGPT。 | 差異化只能來自三件事：記得她、知道什麼時候不回、教練會持續跟進。「記得對象」只勝過繁中鍵盤類 App，英文市場已經有會記得對象的教練 App。 |
| Sydney 教練 | 判斷 8.5/10，邀約時機 4/10，教法本身的一致性 3.5/10，實際輸出的倫理和語氣 8/10。 | 她已經給了機會，卻寫「先不邀約」；被問「你覺得呢」只會反問；prompt 裡有好幾套互相搶優先的決策順序、互相矛盾的問句規則，還有帶 PUA 色彩的舊範例。她主張每次都輸出「教練四件套」：判讀、動作、一句話、一句為什麼；也主張把「點出他自己的錯」（例如連發訊息、像查戶口一樣一直問）當成重點輸出。 |
| 用戶 | 判斷 8/10。 | 開始分析前要做 4 個確認動作；同一句推薦出現兩次；額度單位「則」其實是 40 個字；「她話裡的意思」可能是空白卡。 |

**三方共識：**
- **價值在「判斷」，不在「代寫」。** Sonnet 5.5 在端到端測試裡 23 案的決定全對（`docs/decisions.md` ADR #49），其中 8 個「不回」情境也全部判對（`tools/analyze-v2-blackbox/out/2026-10-02-e2e/arm-C.json`）。
- **最大的漏洞在她問用戶本人的事。** 這時模型會編造（例如「我做業務類的」）、留填空或閃躲。根本原因是分析拿不到用戶本人的資料（`effective_style_prompt_builder.dart:9-25`）。
- **五張風格卡反而稀釋了價值。** 以 thin_opening 這一案為例，五種風格其實只來自三個發想方向；冷讀卡幾乎固定是「我猜…對嗎？」這種句型。其他案例沒有做全面統計。
- **分析頁看不到 Sydney，也看不到記憶。** 模型有寫出「她可能會怎麼回」，但 App 不顯示。

**分歧：**
- **顧問的看法：** 建議改用「可選的替代風格數」和「可再調整的次數」來區分付費方案。這要重新決定 ADR #25（免費方案看得到兩種風格）。
- **用戶視角的看法：** 認為免費額度太小。每月 30 則、每日 15 則（`_shared/quota.ts:19`、`:25`），1 則等於 40 字（`billing.ts`），一張約 400 字的截圖就扣 10 則。

**能不能做到市場最好：** 有機會在「繁中曖昧聊天的下一步」這個小市場做到第一。贏的是判讀準、給一句敢原封送出的話（包括叫他別送、叫他現在約）、記得這個人，不是速度，也不是五種風格。前提有四個：補上用戶本人的資料、第一張卡到了就能複製、邀約和表態交給伺服器規則決定、拿到真實的複製率。市場比較只靠第三方的搜尋結果。

## 4. 等待時間拆解

時間從呼叫模型那一刻開始算，不含之前的步驟。5.5 那一欄的數據來自 `2026-10-02-c-fix` 的送出案（n=39）；Sonnet 5 那一欄來自 `2026-10-02-ab` 的 arm A（n=29）。

| 時間點 | Sonnet 5.5（現行） | Sonnet 5（備援） |
|---|---|---|
| 出現決定 | 3.1 秒 | 4.4 秒 |
| 第一張卡 | 8.5 秒 | 12.4 秒 |
| 五張卡到齊 | 15.1 秒 | 22.7 秒 |
| 完成事件（**現在要到這時才能複製**） | 19.1 秒（p95 23.3 秒） | 33.4 秒 |

決定不回的情況（c-fix，n=24）：約 3.0 秒出現決定，約 8.1 秒完成。

**時間花在哪：**
- **決定到第一張卡，約 5 秒。** 這段輸出約 96% 是「發散計畫」，也就是模型替五張卡先寫的內部規劃，App 看不到。
- **第一張卡到五張卡齊，約 6.5 秒。** 這段是在寫四張替代卡。
- **五張卡到完成，約 3.9 秒。** 這段是數據、教練提示和完成報告。
- **沒量過的部分：** OCR、付費用戶的權益同步（最多 20 秒）、帳號驗證、冷啟動。RevenueCat 補同步沒有設逾時，完成事件也要等紀錄寫完才送出（F38）。
- **沒有首字逾時。** 主模型卡住時，用戶要等滿 120 秒才收到錯誤，備援模型也不會接手（F37，發生頻率未核實）。

**哪些能縮短：**

| 改法 | 預期效果 | 要不要動 prompt |
|---|---|---|
| 第一張卡一到就能複製 | 可複製的時間從約 19 秒降到約 8.5 秒；決定不回時從約 8 秒降到約 3 秒 | 不用 |
| 刪掉發散計畫，或移到後面 | 第一張卡最多再提早約 5 秒（未核實，因為 5.5 有隱藏的思考時間） | 要，而且要先量 |
| 完成事件不再重寫舊報告 | 5.5 提早約 1.3 秒，備援模型提早 6–7 秒 | 要 |
| 減少預設卡數 | 五張卡和完成都會提早，最多約 6.5 秒（估計）；第一張卡時間不變 | 要，而且要重新決定 ADR #25 |
| 加首字逾時 | 只改善模型卡住的少數情況；先量出首字時間，再設在約 20–25 秒 | 不用 |

## 5. 大 prompt 與輸入輸出健檢

實際送出的 v2 串流 prompt 有 48,842 字元，約 39.7K token，是開場救星三份 prompt 加起來（約 4.6K 字元）的 10 倍以上。

| 段落 | 字元數 | 主要問題 |
|---|---|---|
| 推理核心 | 2,707 | 人設還寫著已經不用的「AI 約會教練」（`reasoning_core.ts:3`）；總目標寫「推進邀約」，輸出卻常常不推進。 |
| 對話政策 | 16,090 | 問句規則互相拉扯（`conversation_policy.ts:337` 和 `:386`、`:405` 衝突）；有帶 PUA 色彩的範例（`:18`、`:23`、`:67-68`）。 |
| 回覆語氣 | 3,052 | 「個人化原則」是已經不起作用的規則（`reply_voice.ts:136-150`）。 |
| 報告格式 | 7,156 | 這是第二套、給非串流用的輸出格式；裡面的情境分類欄位沒有程式在讀（`report_contract.ts:60`）。 |
| 舊範例 | 4,966 | 結尾約 1.5K 字的草稿優化段落，串流路徑永遠用不到（`examples_legacy.ts:80`）。 |
| 串流格式 v2 | 約 14.3K | 發散計畫佔 4,809 字；有一句「伺服器會擋並重試」，其實伺服器不會這樣做（`stream_prompt.ts:238`，`:227-236` 的註解自己也承認）；用字串替換的方式改寫選單句（`:141-163`）。 |

**五類毛病：**
- **規則互相打架：**
  - prompt 要求至少一張卡超出用戶平常的風格，但主分析根本拿不到用戶的風格。
  - 「階段」有兩種定義。
  - 要「延伸」話題時要丟回一個小問題，但對方投入低時，問句額度是 0。結果約 9% 的回覆問句超過額度（47/547）。
  - 另外有五套排序清單，每套都說自己最優先。
- **重複：** 「被妳發現了，我會在飲料櫃前思考人生」出現了 3 次。「不要連問清單題，也不要急著跳邀約」出現 2 次，還被模型逐字抄進輸出（e2e C 3/23）。
- **過時：** 結構是舊底座再加上 v2 的條件補丁。雜湊鎖（用 SHA 指紋鎖住 prompt 文字，防止被改動）鎖的是舊版，實際送出的 v2 反而沒鎖（`stream_prompt.ts:36-52`）。
- **沒人用的輸出，以及伺服器私下修正：** 完成事件裡的推薦會被丟掉（`reframer.ts:1473-1490`）；伺服器用同義詞表把「正常進行」對應回 normal（`reframer.ts:1559`）。
- **模型自己替卡片排名：** 伺服器不重排、也不換卡，只靠那句其實不會執行的「伺服器會擋並重試」來施壓（F10）。

**輸入面：**
- 給模型的對話內容是在主函式裡臨時組出來的，整體沒有測試。黑箱評測用的是另一套組法，不帶情境欄位，只測付費方案五種風格的純文字；免費方案、草稿優化、圖片都沒有做過端到端驗證（F22）。
- 對話紀錄沒有編號，引用可能標錯（F07）。
- 時間間隔和「她收回一則訊息」會被丟掉，所以隔三天才回的訊息會被當成連續對話（F48）。
- 長對話的舊摘要是靠關鍵字統計，碰到中文就失效，還取代了對話真正的開頭幾則（F23）。

**輸出面（5.5，c-fix 63 筆合計）：** 回覆卡 36%、發散計畫 15%、數據 13%、完成報告 12%，盤點、決定、教練提示各約 7%。在 5.5 上最值得刪減的是發散計畫；Sonnet 5 時期最大的則是完成報告（約 25–27%）。

## 6. 最重要的問題清單（沒有 P0）

| 級別 | 問題 | 用戶感受 | 證據 | 建議 | 改法類型 |

- 黑箱評測工具。

1. 開一個小 PR 刪掉關鍵字閘門，補上四句正常對話的測試，交給不同家族的模型做主審。

## 10. 給 Bruce 的「不怕改」做法

1. A 階段完成後，只要 CI 通過，就代表整個 analyze-chat 目錄的測試都過了。
2. 一個 PR 只改 prompt，或只改程式，不要兩個一起改。
3. 改伺服器程式時就跑重播測試。結果沒變，代表這些錄下來的案例在內容、扣費、紀錄上都沒變；沒錄到的情況仍要靠其他測試。如果是有意的改動，就重新產生比對基準，在 review 時看差異。
4. 改 prompt 時只改新版那一份，快照的差異會逐行顯示改了什麼。付費黑箱要跑至少 3 輪，差距超過雜訊範圍才算改進；另外再人工標註約 24 張卡，判斷「付費用戶會不會原封送出」。
5. 上線時由 Eric 打開新版開關；出問題就關回去，不用重新部署。
6. 照抄 prompt 的舊測試失敗時，換成檢查「意思對不對」的測試，或交給快照處理；不要改成「檢查 prompt 現在寫了什麼」。改到哪一條就換哪一條。
7. 不必先讀完 48K 字的 prompt。可以從第 5 節的段落表、快照差異和重播結果開始看。
