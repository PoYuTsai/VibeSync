## 總結論

1. **不採全動態生成（AI 憑語境自由生成 5 種風格並命名）**：整體可用性預期是下降，不是上升。
2. **長期終態選 B2（固定核心＋情境槽的池選收斂版，池對齊 coachActionHint actionType）**，但路徑是 A1 → A2 → 用 A2 的遙測數據決定 B2 要不要做、池裡放什麼。A 的每一步都是 B 的地基，沒有丟棄成本。
3. **Codex review 整合後的四軌實作方向**：批次 1（UI 資訊架構）＋獨立軌（口吻偏好學習）立刻做；批次 2（prompt 校準）緊接；批次 3（結構演進 B2）維持條件觸發。

## 第一部分：五種固定風格改為動態生成的評估（2026-08-24）

### 問題

Analyze-chat 的 5 種回覆建議若不先預設「延展、共鳴、調情、冷讀、幽默」5 種固定風格，改請 AI 憑語境生成 5 種適合的風格並命名（如「穩重」「熱情」「情緒價值」「高冷」「霸氣」），回應內容可用性會不會更高？

### 結論：不建議，理由三點

1. 這 5 個名字在系統裡**不是 5 種語氣，而是 5 種接球功能**（延伸話題／接住情緒／製造張力／降壓搞笑／校準猜測），同時是付費牆、串流協議、成效追蹤、安全備援、盲測基準的**契約鍵**——29 個程式檔＋58 個測試檔直接耦合。改成動態等於同時重寫付費結構與品質基建。
2. 提議的範例名**混了兩個軸**：穩重／熱情／高冷／霸氣是「人設語氣軸」——系統已有獨立機制（用戶風格：幽默／穩重／直球／溫柔／調皮型，會調整全部 5 張卡的語氣）；「情緒價值」就是共鳴卡的功能定義。感覺缺的東西多半已存在於別的軸，**是呈現問題，不是能力問題**。
3. 固定制真正的痛點（敏感情境硬產調情卡、「冷讀」太行話）有低風險解法，不必付出全動態的代價。

### 現況：五種風格在系統裡是什麼

產品層是四個獨立的軸：

| 軸 | 內容 | 依據 |
|---|---|---|
| 接法軸（固定 5 風格） | 延展／共鳴／調情／幽默／冷讀＝「這輪怎麼接球」的功能動作，各有品質契約與正反例 | `conversation_policy.ts` 1.8 五種回覆品質契約；ADR #4 |
| 人設軸（用戶風格） | 幽默／穩重／直球／溫柔／調皮型，調整**全部**卡的語氣；「穩重型用戶不給調情當最終建議」 | `session_context.dart`、`reply_voice.ts` 個人化原則 |
| 延伸軸（stretchLevels） | 每張卡相對用戶舒適區 within／stretch／far，至少一張 stretch | `report_contract.ts`、`post_process.ts` Step 2b（關於我重新定位案） |
| 場景軸（scenarioDetected） | 13 種情境矩陣先判斷「該不該出手、出哪招」 | `conversation_policy.ts` 場景觸發矩陣 |

「AI 依語境挑最適合的」現在已經存在——就是 `finalRecommendation.pick`：「AI 推薦」卡永遠排第一張。5 張風格卡是比較貨架，推薦卡才是語境答案。

工程層它們是契約鍵，不是顯示字串：

- **付費牆**：`TIER_FEATURES.free = ["extend","tease"]`（`analyze_chat_handler.ts`）——風格 key 就是訂閱權限 flag（ADR #25：Free 固定延展＋調情）。Paywall 對照表賣「延展＋調情 2 種 vs 全部 5 種」。
- **串流協議**：`STREAM_STYLES` 白名單，未知風格的 reply_option 事件直接丟棄；串流 max tokens 隨風格數計算。
- **成效迴圈**：複製／回報的 adviceId 是決定論的 `analyze:對話:runKey:風格key`——「哪種風格對這個用戶有效」的長期數據靠固定 key 聚合。
- **安全備援**：`getSafeReplies` 句庫按「4 熱度層 × 5 風格」預寫；各風格 fallback 接法與理由都是 switch-case。
- **品質基建**：voice-benchmark 黃金基準與盲測表按 5 風格逐格評分。
- **跨端硬編**：Flutter 卡片標籤／顏色／icon／「為什麼推薦」、串流顯示標籤、onboarding 示範、iOS 鍵盤 extension 的 Swift enum（`KeyboardAPI.swift`）。

### 固定制的真實痛點（動態提議的合理動機）

1. **敏感情境硬湊卡**：吵架、道歉修復、被拒（情境 12）時 schema 仍要求產出調情、幽默卡，prompt 只能用「五種風格都要低壓」去壓——產出是「稀釋版調情」。Free 用戶更尷尬：固定拿到的兩張就是延展＋調情。
2. **同球約束放大相似感**：2026-08-16 拍板五張卡必須接同一組球、段數一致；短回合／冷場時五張卡內容會收斂。
3. **命名偏行話**：「冷讀」對新用戶是黑話、「延展」偏抽象。
4. **個別局面缺第五種功能**：純安慰陪伴、穩定框架不接招、低壓收尾，目前只能塞進 extend／resonate 的皮。

### 全動態生成的代價

**可用性本身**：學習與比較性歸零（每輪發明新分類＝每輪要先讀懂 5 個新名字才能選，time-to-copy 變慢）；重生成不穩定（同一對話重新分析分類每次不同＝「AI 很隨機」）；名字品質與正交性無保證（LLM 常產彼此重疊或半行話的分類；2026-08-17 才處理過冷讀卡混出俄文 token 的真實事故，可見詞彙三層線白名單旁不該再開不受控通道；「霸氣」踩在產品明文反對的油膩／壓迫邊上）；優化錯了對象（「哪種適合此語境」已由推薦卡回答，動態命名優化的是 4 張非推薦卡，卻把主要輸出拖進新失敗面）。

**商業面**：Free「2 種 vs 5 種」失去穩定指涉物。payment/quota 高風險區，需 Eric 拍板＋雙 AI 覆核，且動到送審文案。

**工程面**：schema 從封閉枚舉變開放集合，tier 過濾、串流白名單、備援句庫、outcome 聚合、盲測表、29＋58 個檔案全部重做。

### 範例名的軸線分析

| 提議名 | 實際屬於 | 系統現況 |
|---|---|---|
| 穩重 | 人設語氣軸 | `UserStyle.steady` 已存在，調整全部卡；「穩定回覆原則」也是既有技巧 |
| 熱情 | 人設語氣軸 | 由熱度／投入對等節奏控制，跟著她的投入走 |
| 情緒價值 | 功能軸 | 就是共鳴卡的定義（情境 3 策略原文即「提供情緒價值」） |
| 高冷 | 人設語氣軸 | 與核心人設衝突（情緒穩定 ≠ 高冷）；降投入已有「推」技巧 |
| 霸氣 | 人設語氣軸 | 與減法原則（不做打壓／操控）衝突，是 guardrail 要擋的方向 |

把人設軸塞進接法軸，反而讓「調情的穩重版」這種正確組合（接法 × 人設）無法表達。

### 方案比較（初版）

| | A. 固定骨架＋情境化呈現 | B. 風格池選配 | C. 全動態生成（提議） |

## 第二部分：A、B 方案深度比較與長期路線（2026-08-24 增補）

### 深度比較前查證的關鍵事實

1. **串流是「恰好 N 張」的硬契約**：prompt 明文「Emit exactly N reply_option events」；reframer 以 `requiredReplyStyles` 檢查，缺任何一種風格就發 `STREAM_INCOMPLETE_REPLY_OPTIONS` 錯誤，走已扣費 run 的重試路徑。
2. **串流契約是註記過的高風險 prompt 禁區**：`stream_prompt.ts` 的 floor 威嚇句（2026-06-13 fail-soft，f417bd8）註解明言「改字串＝動高風險 prompt，必黑箱重驗」。
3. **風格集合已經參數化**：`buildStreamSystemPrompt(basePrompt, requestedReplyStyles)`——Free 本來就用 2 種風格跑同一條管線。
4. **Opener 共用同一組 5 個 key**：`OPENER_TYPES` 同為五風格，且有自己的契約 v2（2026-07-24 拍板：Free 恰好三種）；`normalizeStretchLevels` 是兩功能共用的單一事實來源。B 若只改 analyze，風格詞彙就在兩功能間分岔。
5. **「這次先不推」的語意載體已存在**：stretchLevel 已逐卡串流（far＝差距太大這次先不推）。
6. **UI 硬編點集中可枚舉**：labels／理由／顏色（`reply_style_card.dart`）、icons（`app_icons.dart`）、premiumDefault 判斷、串流顯示標籤。

### 方案拆解

- **A1（呈現層）**：卡頭改「動態副標為主（approach 已存在）、固定名退小字」＋行話名文案調整＋far 卡降權顯示。零 server 契約改動、不碰 prompt 禁區。
- **A2（情境出口，增量欄位）**：reply_option 加選填欄位（如 `fitThisRound: recommended | ok | notAdvised`）。敏感情境模型標「這輪不建議調情」，UI 摺疊降權，**卡張數不變**——不破「付費 5 種」承諾、不碰 exactly-N floor、舊 client 向後相容。不採「缺卡」版：缺卡觸發串流錯誤、破壞付費承諾。
- **B1（server 預選）**：打模型前 server 不知道情境（scenarioDetected 是模型輸出），需前置分類呼叫或啟發式。捨棄。
- **B2（model 池選，收斂版）**：server 維護固定風格池（封閉枚舉，約 9–10 個），模型每輪輸出恰好 5 張——延展、共鳴常駐，其餘 3 槽依情境從池選（正常聊天選調情／幽默／冷讀＝現狀；修復／複雜情緒選安慰陪伴／穩定框架／低壓收尾等）。Free 維持固定延展＋調情（ADR #25 不動）。**池直接對齊 coachActionHint 的 9 個 actionType**——系統已有一份策展過的情境動作詞彙，不必發明新分類。

### 維度逐項比較（A1／A2／B2）

| 維度 | A1 呈現層 | A2 增量欄位 | B2 池選收斂版 |
|---|---|---|---|
| 敏感情境硬湊卡 | 部分（副標誠實說明，內容仍稀釋版） | 大部分（標注＋降權） | **完全（換成適合的接法卡）** |
| 行話名 | 完全（文案層） | — | 完全 |
| 缺第五種功能 | 否 | 否 | **是** |
| 學習／比較性 | 保留 | 保留 | 保留，但詞彙 5→約 10，教學面加倍 |
| 付費牆／文案 | 不動 | 不動 | 對照表與升級文案需改寫（Free 不動） |
| Server 改動 | 無 | 小（+1 選填欄位、sanitize、reframer 透傳） | 中大（契約語意、TIER_FEATURES、池定義、備援句庫×4 熱度、fallback 文案） |
| Prompt 風險 | 低（不碰禁區） | 中（碰串流契約→黑箱重驗一輪） | 高（大改契約＋選配新行為→完整黑箱＋盲測） |
| 測試／基準 | 少量 widget 測試 | 中 | 大（58 測試檔多數要動＋voice-benchmark 重排） |
| Outcome 數據 | 完整延續 | 完整延續＋**新增 notAdvised 訊號** | key 穩定可聚合，但樣本變稀＋選配偏差 |
| 跨功能一致性 | 完整 | 完整 | 連帶決策（Opener／鍵盤／練習／文章是否跟進） |
| 新失敗模式 | 無 | flag 誤標（低危害） | **選錯池**（中危害：正常聊天少了調情卡＝付費體驗變動）；outage fallback 到 Haiku 時更難保 |
| 可回退性 | 即時 | 即時（忽略 flag） | 難 |
| 工時（一 PR 一目的估算） | 1–2 個 PR | 2–3 個 PR | 6–10 個 PR＋黑箱／盲測輪 |

### 長期路線結論

1. **長期正確的終態是 B2 收斂版**——唯一能把「判斷局勢」的產品差異化落到卡片層的方案。前提是數據證明需要。
2. **現在直接做 B 是在沒有需求數據下押大改動**：敏感情境實際占比未知。
3. **A 不是 B 的競爭方案，是 B 的第一、二里程碑**：副標主視覺、降權 UI、fitThisRound 欄位、黑箱重驗流程，全部是 B 的地基。
4. **B 的觸發條件**：(a) notAdvised 標記率（例如持續 >15%）；(b) 被標卡的複製率低；(c) 離線盲測（固定 5 vs 池選 5）勝出。三條件齊了再動 schema。

## 第三部分：Codex Review 嚴格審視與整合（2026-08-25 增補）

### 它評的是哪份文件

Codex 打不開本報告的 Artifact（私人預設，外部看到 Page not found），實際審的是分支上另一份 R1–R5 舊研究報告（公式填空感／結構壓力／同質化／強制風格／模型 token 不足），**不是本報告**。值得注意：Codex 的 P0「以 actionType 決定策略、語氣為第二層」與本報告 B2 收斂版是**兩個獨立 AI 各自收斂到同一方向**——方向正確性的旁證。分歧在「何時做」：它當 P0 立即改，本報告主張條件觸發。

### 事實查核（已對最新 main `2cd926c` 複驗）

**屬實**：token 預算 4500／6000（`stream_budget.ts`）；全 tier Sonnet 5；opener 已移出 analyze prompt（`system_prompt.ts` 組成無 opener 段）；恰好 3 組完整範例（`examples_legacy.ts`）；免費固定延展＋調情；推薦卡逐段顯示原句／回覆／理由／複製／微調；「再調一下」已實作且快捷鍵刻意只留收斂方向（太油／短一點／白話一點／溫和一點）。

**三個關鍵誤讀**：

1. **floor 不是硬 enforcement**。「server rejects」威嚇句自 2026-06-13（f417bd8）起是 fail-soft：server 不 reject 不 retry，違反只記 log；註解明言這句是刻意保留的 compliance 壓力、「改字串＝必黑箱重驗」。「解除逐球分段壓力」沒有機制可拆，正確槓桿是 prompt 校準（接／併／略判準），且該區是禁區。
2. **「五風格需要時才生成」踩中扣費模型**。配額次數制、串流一次扣費、exactly-once 帳本是刻意的單一路徑；第二次生成＝第二次請求＝計費設計問題。安全版是**同次生成、預設收合**（純 UI 摺疊）。
3. **免費層改「推薦＋情境適配替代版」不是 P0**。(a) 風格集合在打模型前就由 `TIER_FEATURES` 決定，server 事前不知情境；讓模型請求內選第二張＝改串流契約。(b) ADR #25 的「2 vs 5」是付費對照表賣點結構，屬 payment 高風險區。方向有價值，歸批次 3。

**Codex 還漏了一個回歸風險**：同球對齊＋段數下限是 2026-08-09 真機 telemetry 抓到「非選中卡漏球」後的修復，2026-08-16 同組球拍板是為了「不讓使用者以為漏回」。把這套結構當純壓力源，沒回答「拆了之後漏球怎麼防」；其驗收指標組也缺漏球率——放鬆段數壓力時必須同時監控 ball_coverage。

### 逐項處置

| Codex 建議 | 處置 | 理由 |
|---|---|---|
| P0：一個決策＋三個版本、五風格收「更多接法」 | 改造採納 | 呈現方向對；「需要時才生成」改同次生成＋預設收合；完整結構落批次 3（B2 終態的呈現語言） |
| P0：預設只 1–2 則訊息、條件才 3 則 | **拒絕硬上限** | 與 2026-08-16 同組球拍板及漏球修復對撞；現行規則本就是「段數跟真球數走、寧可少一段紮實」——差距在校準不在規則 |
| P0：actionType 決定策略、免費改適配版 | 方向採納、時點不採 | ＝B2 收斂版（獨立收斂旁證）；成本與風險不因換說法消失，維持條件觸發 |
| P1：UI 資訊密度精簡、漸進展開 | 採納 | 併入批次 1；引用原句是信任功能（一球一回批），改預設收合、一鍵展開，不移除 |
